## Part 2: Fault Tolerance in DSFS
Now, I will take an overview of how the system manages fault tolerance. Specifically, it details the system's response to two primary failure scenarios: a server crash during a read operation and a client crash during a write operation. It also explores the underlying mechanisms that make this resilience possible, including retry logic, leader redirection, and exponential backoff.
### System Architecture and Reliability Design
 At its core, the system architecture is divided into a client side, which serves as the entry point for applications, and a server side, where files are stored and replicated. The client side intercepts operations and forwards them to a replicated client implementation, while the server handles the underlying storage logic.
To ensure reliability, the system relies on several key design choices. Most importantly, it employs commit-on-close semantics. This means that client-side writes only update a local cached copy of the file initially; the server's state is permanently committed only when the close function is successfully called. To prevent stale reads, the client maintains a versioned cache that it validates against the server's version. Furthermore, the system is leader-aware: if a write request is sent to a non-primary server, the client receives a redirect notification and automatically retries the operation with the correct primary node.
### Surviving Server Crashes During Reads (Test Case 2A) 
The system's ability to handle a server crash during a read operation is validated by simulating a sudden server failure. In this scenario, a server is started with a persistent data directory, a large file is committed, and then the server process is abruptly killed before a read operation can occur. Naturally, the immediate read attempt by the client fails.
However, when the server is restarted using the same data directory, the client's subsequent read attempts-executed in an automated loop-eventually succeed. This recovery is possible because the committed file bytes survive the process crash by resting safely on the disk. The client's built-in retry logic absorbs any startup delays or readiness windows, ensuring it successfully fetches the data once the server is back online.
### Surviving Client Crashes During Writes (Test Case 2B) 
Conversely, the system must also protect the server's data integrity if a client crashes mid-write. This scenario is tested by having an initial client write and successfully close a file to establish a baseline. A second client then opens the file, writes new data to it, but simulates a crash by disconnecting before calling the close function.
Because of the system's strict commit boundary, these unclosed bytes are never committed to the server. When a third client subsequently reads the file, it will find that the original baseline content and the file version remain entirely unchanged. This architecture guarantees that incomplete client transactions never corrupt the committed server state.
### Exponential Backoff and Leader Redirection 
To handle transient network issues or temporary outages, the client implements an exponential backoff strategy for specific gRPC errors, such as unavailable services, exceeded deadlines, or exhausted resources. When these errors occur, the client pauses for a delay that grows exponentially based on the number of attempts, rediscovers the primary server from the cluster, and retries the request. This approach seems to be effective for surviving short server restarts, leader election windows, and temporary network instability.
Additionally, if the cluster undergoes a topology change, a server might respond with a "not primary" error containing the new primary's address. The client seamlessly parses this new address, updates its target, and retries the request transparently. This allows writes to continue flowing across failover transitions without requiring any manual reconfiguration.
### Demonstration and Scope 
These fault-tolerance behaviors can be observed by executing the designated Task 2 shell script, which runs both the server crash and client crash test runners and outputs a pass summary. It is important to note that these specific tests are strictly focused on validating the fault tolerance of the file server operations themselves. They do not validate broader coordinator-worker behaviors, which are evaluated in a separate phase of testing.
### The Mental Model 
To quickly conceptualize the system, think of the open, read, and write operations as occurring on a local working stage combined with remote RPC calls. The close operation serves as the definitive transaction commit point. Meanwhile, automated retries with backoff help the system survive temporary failures, and leader redirection ensures it can seamlessly adapt to cluster topology changes. Together, these mechanisms guarantee that server data remains uncorrupted by client crashes and accessible despite temporary server outages.
