## Part 2: Fault Tolerance in DSFS
In this part I describe how my file system handles faults: what happens when a server crashes during a read, what happens when a client crashes during a write, and the mechanisms that make recovery work (retry logic, leader redirection and exponential backoff).
### System Architecture and Reliability Design
I split the system into a client side, which applications call into, and a server side, where files are stored and replicated. The client side intercepts operations and forwards them to a replicated client implementation, while the server handles the storage logic.
Reliability comes from a few design choices. The most important is commit-on-close: a client's writes only update a local cached copy of the file, and the server's state changes only when `close` succeeds. To prevent stale reads, the client keeps a versioned cache that it validates against the server's version. The client is also leader-aware: if it sends a write to a server that isn't the primary, it gets a redirect and retries the operation on the correct primary.
### Surviving Server Crashes During Reads (Test Case 2A)
To test a server crash during a read, I start a server with a persistent data directory, commit a large file, and then kill the server process before the read happens. The client's first read attempt fails, as expected.
When I restart the server on the same data directory, the client's retried reads, run in a loop, eventually succeed. This works because the committed file bytes are on disk and survive the crash, and the client's retry logic absorbs the delay while the server starts up.
### Surviving Client Crashes During Writes (Test Case 2B)
A client crashing mid-write must not damage the server's data. To test this, a first client writes and closes a file to set a baseline. A second client then opens the file and writes new data, but disconnects before calling `close`, simulating a crash.
Because writes only commit on `close`, those unclosed bytes never reach the server. When a third client reads the file, the baseline content and the file version are unchanged, so an incomplete client transaction can't corrupt the committed server state.
### Exponential Backoff and Leader Redirection
For transient network problems and short outages, the client retries specific gRPC errors (unavailable, deadline exceeded, resource exhausted) with exponential backoff: it waits for a delay that grows with each attempt, rediscovers the primary from the cluster, and retries the request. This seems to be effective for surviving short server restarts, leader-election windows and temporary network instability.
If the cluster's topology changes, a server may answer with a "not primary" error that carries the new primary's address. The client parses that address, switches to it and retries the request, so writes keep flowing across a failover without any manual reconfiguration.
### Demonstration and Scope
The Task 2 shell script demonstrates these behaviours: it runs both the server-crash and the client-crash tests and prints a pass summary. These tests only cover the fault tolerance of the file-server operations; I test the coordinator-worker behaviour separately, in a later phase.
### How I Think About It
I think of `open`, `read` and `write` as work on a local staging copy, with RPCs to the server around it, and of `close` as the commit point. Retries with backoff carry the client through temporary failures, and leader redirection lets it follow topology changes. Between them, server data stays safe from client crashes and available through short server outages.
